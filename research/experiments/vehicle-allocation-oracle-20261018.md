# Preregistered vehicle-task assignment oracle gate

Baseline is unchanged scalable_junction_simulator.cu at repository b785498. Frozen inputs: berkeley-allocation-workloads-20261018, all 24 cases, matched snapshots 60/180/300/450 s (96). Fixed 128-thread blocks. Three process batches, three warmups and ten randomized evaluation repetitions per configuration. CPU/GPU clocks fixed and restored. No tuning using test timings.

All assignment policies use one generated advanceTasks kernel derived verbatim from the original advance body: only slot-to-stable-ID mapping is added. Original advance remains the direct baseline. Timed template instantiation has no instrumentation. State storage, calculation order within each vehicle, leader indexes, motion context, and downstream junction stages are identical. Every record including pending/completed appears exactly once. Full Car bytes, motion outputs and all semantic junction summaries must match the direct baseline. Index construction and junction stages remain in complete-step timings.

Policies: direct original; identity indirection; geographic order (region then lane then position, cut into fixed-size blocks); vehicle-count balance (road-active IDs striped evenly among blocks, other records fill remaining slots); state grouping (state, near-end indicator, stopped/moving, region, lane); oracle grouped; oracle balanced. Geography is fixed-size spatially ordered batches, not equal geographic area or variable block size. State grouping tests similar branch paths; oracle balancing tests measured-cost distribution.

Oracle candidate units are 32-ID microbatches from vehicle-count assignment, preserving each microbatch's internal IDs. Measure each microbatch's maximum per-lane elapsed clock64 cycles in five separate instrumented fitting passes, use the median. These are contextual warp costs observed within the calibration grid, not standalone execution times or independent additive task costs. Grouped oracle sorts microbatches by measured cost; balanced oracle assigns descending cost microbatches greedily to lowest estimated-load blocks, at most four microbatches/block. No evaluation sample chooses or retunes the oracle schedule. Instrumentation only in fitting; fitting overhead is recorded and charged in the inclusive mode. Oracle is a candidate, not an optimality bound.

Two cost modes: supplied-free schedules (all construction/transfer/fitting excluded, held fixed) and charged per step (state download, CPU list construction, H2D task-list transfer, and oracle fitting included). Persistent buffer allocation excluded for all. CUDA events split common pre-index work, vehicle update, downstream junction work, complete pipeline and charged setup; host elapsed includes launches and final synchronization. Input resets and validation are outside timing. The complete step is the computational step, excluding simulation-output I/O and the host correctness checker.

Gate fixed before data: on the frozen test cases, a nonbaseline policy must reduce median charged complete-step wall time by >=5% versus vehicle-count assignment in EACH of three process batches, win on >=75% of the 60 distinct test snapshots using across-batch median ratios, and have zero correctness failures. Also report comparison with original direct implementation and identity overhead. Supplied-free results show possible amortized opportunity but cannot pass the charged gate. Report train/validation/test separately and inspect demand-level regressions. No learned prior or new network generalization claim in this phase. Schedule-stability/amortization is not assumed.
